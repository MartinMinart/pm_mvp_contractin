
# Модель данных Event Log для Process Mining MVP

Этот документ — модель данных Event Log. Он описывает, как из сырых событий собрать корректный лог для Process Mining. Здесь зафиксированы правила склейки кейсов и S2T-маппинга (Source-to-Target) из систем-источников (SAP) в наши CSV-файлы.

**Версия:** 1.0
**Основа:** `АЛГОРИТМ КИП итог` (ЕвроХим) + адаптация под закупки/контрактацию.

---

## 1. Назначение

Этот документ описывает, **как из сырых событий собрать корректный event log** для Process Mining. Ключевой принцип: **без корректного event log любой анализ даст «мусор»**.

Модель данных состоит из двух таблиц:
- **`cases.csv`** — атрибуты кейса (одна строка = один кейс).
- **`events.csv`** — события (одна строка = одно событие в кейсе).

## 2. Границы процесса

**Анализируемый процесс:** «Закупка → Контрактация → Исполнение» для горнодобывающего холдинга (ЗИП, расходники, спецтехника, подряд).

| Параметр | Значение |
|---|---|
| **Старт** | `Requisition Created` (заявка создана) |
| **Конец** | `Payment Made` (оплата произведена) |
| **Сквозной идентификатор** | `case_id` (например, `CASE-000001`) |
| **Объекты контроля** | Заявка (Requisition), Договор (Contract), Платёж (Payment) |
| **Единица анализа** | Один кейс = одна закупка от заявки до оплаты |

## 3. Схема `cases.csv`

Одна строка = один кейс.

| Поле | Тип | Обязательно | Описание | Пример |
|---|---|---|---|---|
| `case_id` | string | Да | Уникальный ID кейса | `CASE-000001` |
| `category` | string | Да | Категория закупки | `ЗИП (запчасти)` |
| `procurement_type` | string | Да | Тип закупки | `Тендер` |
| `region` | string | Да | Регион | `Кировск` |
| `department` | string | Да | Подразделение-инициатор | `Горный департамент` |
| `supplier` | string | Да | Поставщик | `Поставщик_042` |
| `amount` | float | Да | Сумма контракта, руб | `1234567.89` |
| `downtime_cost_per_day` | int | Да | Стоимость простоя, руб/день | `1500000` |
| `is_import` | int (0/1) | Да | Импортный кейс (таможня) | `1` |
| `is_rejected` | int (0/1) | Да | Отменённый кейс | `0` |
| `start_date` | ISO 8601 | Да | Дата старта кейса | `2024-03-15T09:00:00` |
| `end_date` | ISO 8601 | Нет | Дата завершения | `2024-05-20T17:30:00` |
| `duration_days` | float | Нет | Длительность кейса, дней | `66.35` |
| `total_cost_of_delay` | float | Нет | `duration_days × downtime_cost_per_day` | `99525000.0` |

> **Фактическая схема v1.0 (2026-10-31).** В сгенерированном `cases.csv` — 11 колонок:
> `case_id, category, procurement_type, region, department, supplier, currency, amount,
> downtime_cost_per_day, is_import, is_rejected`. Полей `start_date`, `end_date`, `duration_days`,
> `total_cost_of_delay` в файле **нет**: они вычисляются агрегаторами (`tools/csv_to_json.py`,
> `notebooks/01_pm4py_analysis.ipynb`) из `events.csv`. Обоснование — `docs/decision-log.md`, DATA-T4-01.

## 4. Схема `events.csv`

Одна строка = одно событие в кейсе. **Денормализована**: атрибуты кейса дублируются в каждом событии (для удобства загрузки в pm4py).

| Поле | Тип | Обязательно | Описание | Пример |
|---|---|---|---|---|
| `case_id` | string | Да | ID кейса (FK → `cases.case_id`) | `CASE-000001` |
| `activity` | string | Да | Название активности | `Requisition Created` |
| `timestamp` | ISO 8601 | Да | Время события | `2024-03-15T09:00:00` |
| `resource` | string | Да | Роль исполнителя | `Специалист по закупкам` |
| `phase` | string | Да | Фаза процесса | `sourcing` |
| `source_system` | string | Да | Система-источник | `SAP SRM` |
| `document_type` | string | Нет | Тип документа (пока пусто) | `` |
| `document_status` | string | Нет | Статус документа (пока пусто) | `` |
| `category` | string | Да | (из `cases`) | `ЗИП (запчасти)` |
| `procurement_type` | string | Да | (из `cases`) | `Тендер` |
| `region` | string | Да | (из `cases`) | `Кировск` |
| `department` | string | Да | (из `cases`) | `Горный департамент` |
| `supplier` | string | Да | (из `cases`) | `Поставщик_042` |
| `amount` | float | Да | (из `cases`) | `1234567.89` |
| `is_import` | int | Да | (из `cases`) | `1` |
| `is_rejected` | int | Да | (из `cases`) | `0` |
| `downtime_cost_per_day` | int | Да | (из `cases`) | `1500000` |

## 5. Правила склейки кейсов (Case ID)

**Сквозной идентификатор** = `case_id` (например, `CASE-000001`). Он назначается **при создании заявки** (`Requisition Created`) и **не меняется** до `Payment Made`.

### Правила:

1. **Один кейс = один `case_id`.** Не должно быть двух `case_id` для одной закупки.
2. **`case_id` генерируется** на этапе `Requisition Created` (в реальной системе — это номер заявки / `Requisition ID`).
3. **Связь с документами:** в реальной системе `case_id` = `Requisition ID`, к которому привязаны `Contract ID`, `PO ID`, `Invoice ID`. В MVP — один `case_id` на всё.
4. **Связь с родительским кейсом (второй этап):** если закупка разбивается на несколько договоров, используется `parent_case_id`. В MVP — **не используется**.

### Почему это важно:
Если `case_id` назначить неправильно (например, по номеру договора, а не заявки), то часть событий (согласование, RFQ) «потеряется», и Process Mining покажет неполный маршрут.

## 6. Правила формирования сессий (по мотивам `АЛГОРИТМ КИП`)

В `АЛГОРИТМ КИП` описано правило сессий: **разрыв > 5 минут → новая сессия**. Для нашего процесса (закупки) **сессии не используются** — единица анализа = `case_id`, а не сессия пользователя. Однако правило полезно для **будущего анализа действий пользователей** (если будем строить `user_sessions`).

### Правило сессий (на будущее):
- Сессия = непрерывная последовательность событий **одного пользователя**, где `timestamp` следующего события − `timestamp` предыдущего ≤ 5 минут.
- Если разрыв > 5 минут — новая сессия.
- Если пользователь сменился — новая сессия.

## 7. Дедупликация событий

**Проблема:** в реальных логах одно и то же событие может дублироваться (повторный вход на страницу, повторная загрузка).

**Правило:**
1. Дедупликация по ключу `(case_id, activity, timestamp)` — если три поля совпадают, оставляем одно событие.
2. Если `timestamp` отличается (разные миллисекунды) — считаем разными событиями.
3. Если `activity` отличается, но `timestamp` и `case_id` совпадают — **аномалия**, логируем в `logs/validate_warnings.log`.

**В генераторе:** дедупликация не нужна (синтетика чистая), но `validate.py` проверяет дубли и предупреждает.

## 8. Синхронизация времени

**Проблема:** в реальных системах время может рассинхронизироваться (SCADA отстаёт на 5 минут, часовой пояс).

**Правило:**
1. Все `timestamp` — в **UTC** (или в одном часовом поясе).
2. В `validate.py` проверка: `timestamp` внутри кейса **монотонно возрастает**. Если нет — кейс помечается как «аномалия», исключается из DFG.
3. В MVP — синтетика уже монотонна, проверка простая.

## 9. S2T-маппинг (Source-to-Target)

Для реальной интеграции (второй этап) — таблица соответствия полей.

| Источник (SAP SRM / ERP) | Целевое поле (`events.csv`) | Трансформация |
|---|---|---|
| `REQ_ID` | `case_id` | `'CASE-' + lpad(REQ_ID, 6, '0')` |
| `ACTIVITY_CODE` | `activity` | Маппинг через `activity_dictionary.md` |
| `EVENT_TIMESTAMP` | `timestamp` | `to_iso8601(ts)` |
| `USER_ROLE` | `resource` | Маппинг через справочник ролей |
| `PROCESS_PHASE` | `phase` | Константа по активности |
| `SYSTEM_NAME` | `source_system` | Константа по источнику |
| `CATEGORY_ID` | `category` | JOIN со справочником категорий |
| `PROC_TYPE` | `procurement_type` | Константа |
| `REGION_ID` | `region` | JOIN со справочником регионов |
| `DEPT_ID` | `department` | JOIN со справочником подразделений |
| `SUPPLIER_ID` | `supplier` | `'Поставщик_' + lpad(SUPPLIER_ID, 3, '0')` |
| `AMOUNT_RUB` | `amount` | `cast(amount as float)` |
| `DOWNTIME_COST` | `downtime_cost_per_day` | Константа по категории |

**В MVP** — не используется (синтетика уже в целевом формате). Но документ важен для второго этапа.

## 10. Валидация (что проверяет `validate.py`)

| Проверка | Что делает | Действие при ошибке |
|---|---|---|
| Колонки | Все обязательные поля присутствуют | FAIL |
| NULL в `case_id`, `timestamp` | Нет пропусков | FAIL |
| Монотонность `timestamp` внутри кейса | `timestamp[i] >= timestamp[i-1]` | WARN (кейс исключается из DFG) |
| Дубли `(case_id, activity, timestamp)` | Нет дублей | WARN (дедупликация) |
| Все `case_id` из `events.csv` есть в `cases.csv` | Referential integrity | FAIL |
| `is_import = 1` → есть `Customs Clearance` | Логическая согласованность | WARN |
| `is_rejected = 1` → есть `is_rejected = 0` в `cases.csv` | Логическая согласованность | WARN |
| Валидные `timestamp` | Парсятся как ISO 8601 | FAIL |
