## ADR-T3-01: Graphviz как системная зависимость для рендера графов

**Дата:** 2026-10-30
**Контекст (Task 3, ноутбук `01_pm4py_analysis.ipynb`):** `pm4py.view_dfg()` / `save_vis_dfg()` /
`save_vis_petri_net()` вызывают внешний бинарник `dot`. На стенде python-пакет `graphviz 0.21` был
установлен, но `dot.exe` отсутствовал → `ExecutableNotFound`, то есть AC-9 (3 PNG) не выполнялся.

**Решение:** установить официальный дистрибутив Graphviz (`winget install --id Graphviz.Graphviz -e`,
версия 16.1.0) и добавить `C:\Program Files\Graphviz\bin` в пользовательский `PATH`. Ноутбук использует
нативные функции pm4py без собственных рендереров.

**Альтернативы:**
- *Собственный рендер DFG/Petri на matplotlib+networkx* — не требует бинарников, но добавляет
  `networkx` в прямые зависимости и ~50 строк кода обвязки; картинки хуже читаются и расходятся
  с «каноническим» видом pm4py.
- *Гибрид (dot если есть, иначе fallback)* — максимальная переносимость, но две ветки рендера
  и риск, что у разных людей в README окажутся разные картинки.

**Следствия / риски:**
- Graphviz нужен только для ноутбука; сайт (`Plotly.js`) и `csv_to_json.py` от него не зависят.
- В `requirements.txt` добавлен комментарий-инструкция: pip-пакет `graphviz` сам по себе бинарник не ставит.
- Windows-путь в `PATH` машинно-специфичен; на другой машине нужен свой `dot` в `PATH`.

## DATA-T3-01: В `cases.csv` нет `duration_days` / `total_cost_of_delay`

**Дата:** 2026-10-30
**Факт:** `spec/data_model.md` §3 описывает `cases.csv` с полями `start_date`, `end_date`,
`duration_days`, `total_cost_of_delay`. Фактический файл содержит 11 колонок
(`case_id, category, procurement_type, region, department, supplier, currency, amount,
downtime_cost_per_day, is_import, is_rejected`) — перечисленных полей нет.

**Решение:** стоимость простоя считается в ноутбуке из событий:
`duration_days = (max(timestamp) − min(timestamp)) по кейсу`, затем
`Σ duration_days × downtime_cost_per_day` (AC-4). `cases.csv` не изменялся,
генератор не перегенерировался.

**Проверка согласованности:** сумма совпала с `site/data/overview.json` (Task 2) до копейки —
534 392 476 278 ₽; средняя длительность кейса 35.675 дн в обоих расчётах.

**Открытый вопрос:** либо обновить `spec/data_model.md` §3 под фактическую схему `cases.csv`,
либо добавить поля в генератор (потребует регенерации 272 МБ данных). Требует решения владельца.

**Решение (2026-10-31):** правим доку, генератор не меняем — см. DATA-T4-01.

## AC-T3-01: AC-5 (топ-1 вариант ≥ 30% кейсов) не достигается на текущих данных

**Дата:** 2026-10-30
**Факт:** в логе 80 вариантов процесса. Самый частый (без таможни, без переговоров, без возвратов)
покрывает 12 811 кейсов = **25.62%** — ниже порога AC-5 (≥ 30%).
Значение совпадает с `site/data/variants.json` (Task 2), то есть расхождение не в расчёте.

**Причина:** вариативность генератора складывается из четырёх независимых факторов
(`is_import` ~38% кейсов, «единственный поставщик» ~25%, переговоры ~30%, возврат на юр. экспертизу ~15%),
что даёт 80 комбинаций и «размазывает» распределение.

**Решение в Task 3:** порог AC-5 **не подгонялся**. Ноутбук считает факт и выводит `FAIL` в
самопроверке (ячейка 8); в отчёте зафиксировано расхождение.

**Варианты закрытия (нужно решение владельца):**
1. Смягчить AC-5 до «топ-1 ≥ 25%» (факт 25.62%) и зафиксировать обоснование в `spec.md`.
2. Снизить вариативность генератора (например, привязать переговоры к одной категории) и перегенерировать данные.
3. Оставить как есть: 80 вариантов — реалистичная картина для закупок, а AC-5 признать недостижимым для MVP.

## DATA-T3-02: Ожидание на `Customs Clearance` обрезано 30 днями

**Дата:** 2026-10-30
**Факт:** в генераторе время до следующего события для `Customs Clearance` ограничено сверху
30 днями (2 080 событий имеют ровно 30.0 дн). Следствие: `P90 = max = 30 дн`, поэтому
«доля кейсов с задержкой > P90» для этой активности равна **0%** — метрика вырождена.

**Решение:** ноутбук показывает факт и поясняет причину в markdown-ячейке; формула AC-6
(строгое `> P90`) не менялась, чтобы не подгонять результат.

**Следствия:** в топ-3 по вкладу в длительность `Customs Clearance` не попал (11.29% против 13.06%
у `Legal Review Started`), хотя среднее ожидание у него максимальное (10.62 дн) — из-за малой доли
импортных кейсов (18 967 событий из 1.09 млн). Для честного сравнения активностей с разной долей
кейсов нужна нормировка (см. `spec.md` §11, примечание к bottleneck_score) — в MVP не делаем.

## TOOL-T3-01: Особенности pm4py 2.7.23.11 на pandas 3.0.6 / Python 3.14

**Дата:** 2026-10-30
Зафиксировано по факту отладки (сэкономит время на следующем ноутбуке):

1. `pm4py.format_dataframe()` **мутирует переданный DataFrame** (добавляет `case:concept:name`,
   `concept:name`, `time:timestamp`) и возвращает копию с двумя служебными колонками
   `@@index` / `@@case_index`. Повторный `rename` этих колонок создаёт дубликаты и ломает
   `discover_dfg` (`AttributeError: 'DataFrame' object has no attribute 'dtype'`).
2. `pm4py.get_variants()` и `get_variants_as_tuples()` возвращают `dict[variant] → int` (число кейсов),
   **не список кейсов** — `len(value)` падает с `TypeError`.
3. `save_vis_*` возвращает `None` (файл пишется по пути), а `view_*` в headless-режиме пытается
   открыть просмотрщик — для nbconvert используем только `save_vis_*`.
4. Баннер лицензии pm4py печатается в `stderr` при импорте из `__main__`; в ноутбуке гасится
   через `contextlib.redirect_stderr`.
5. `rankdir="TB"` даёт читаемый результат (DFG 1079×3135 px), `LR` — полосу 896×7283 px.

## DATA-T4-02: `bottleneck_score` нормируется на `share_of_cases`

**Дата:** 2026-10-31
**Проблема:** сырой скор `(avg_days / Σ avg_days) × std_days` не учитывает, что активность может
встречаться в меньшей доле кейсов. `Customs Clearance` (10.62 дн) получал 2.2855 против 0.35
у процессных этапов — разрыв в 6.5 раза, хотя кейсов с таможней 37.9%.
**Решение:** `bottleneck_score_normalized = bottleneck_score × share_of_cases`,
где `share_of_cases = transitions / total_cases` (может быть > 1 у активностей с возвратами —
это «переходов на кейс», а не доля).
**Эффект:** `Customs Clearance` 2.2855 → **0.8670** (в 2.2 раза выше следующего, а не в 6.5).
Топ-3 меняется: было `Customs Clearance, Legal Review Started, Technical Review Completed`,
стало `Customs Clearance, Legal Review Started, Legal Review Completed`.
В JSON оба скора: сырой (`bottleneck_score`) и нормированный (`bottleneck_score_normalized`);
сортировка — по нормированному.

## DATA-T4-03: Process Map — `scatter` + кастомные линии, а не Sankey

**Дата:** 2026-10-31
**Проблема:** `spec/design.md` §6.5 предлагал Sankey. Sankey не умеет обратные петли, а в логе их
три значимых (`Legal Review Completed → Draft Contract Created` 7 412, `→ Negotiation Started` 14 608,
`Goods Shipped → Customs Clearance` 18 967). Плюс 25 узлов и 28 рёбер в Sankey дают нечитаемое
переплетение и не дают кликнуть по конкретному ребру.
**Решение:** Plotly `scatter` (узлы) + `scatter` с `line.shape="spline"` (рёбра), координаты узлов —
из `avg_position` (средний индекс события в кейсе). Толщина ребра — логарифм частоты, цвет — тип узла
(`start` / `end` / `bottleneck` / `normal`). Справа — сайдбар топ-10 переходов, клик по ребру открывает
drill-down. Легенда обязательна.
**Следствие:** `spec/design.md` §6.5 переписан под этот вариант.

## DATA-T4-04: `monthly` считается по месяцу старта кейса

**Дата:** 2026-10-31
**Проблема:** в первой версии `overview.json` кейсы группировались по месяцу **события**, поэтому кейс
длиной 3 месяца попадал в каждый месяц, а сумма по месяцам превышала 50 000. Для графика «длительность
по месяцам» и `best_month` / `worst_month` это некорректная база.
**Решение:** группировка по `start_month` (месяц первого события кейса). Сумма `cases` = 50 000,
`avg_duration_days` и `total_cost` считаются по кейсам.
**Следствие:** ряд стал короче — 12 месяцев (2024-01 … 2024-12), а не 13, потому что кейсы стартуют
только в 2024 году (последние события — декабрь 2024; канон периода — DATA-T4-08). Для событийной хронологии на сайте используется
`monthly_by_category` и `total_events`.

## DATA-T4-05: `cost_of_delay_rub` — честная сумма потерь, а не «средняя цена дня × срок»

**Дата:** 2026-10-31
**Проблема:** в первой версии `cost_of_delay_rub = avg_days × mean(downtime_cost_per_day)` — это не сумма
потерь, а произведение средних. Такая колонка «стоимость простоя» в UI вводит в заблуждение
(у `Customs Clearance` выходило 3.18 млн ₽ при 18 967 переходах).
**Решение:** `cost_of_delay_rub = Σ (wait_days × downtime_cost_per_day)` по всем ожиданиям активности,
где `downtime_cost_per_day` берётся из того кейса, к которому относится ожидание.
**Проверка:** сумма по 24 активностям = **534 392 476 278 ₽** — ровно `overview.total_cost` (AC-4),
то есть ни одно ожидание не потеряно и не посчитано дважды.
**Следствие:** появляется второй срез для той же таблицы — «дорого на кейс» (`Customs Clearance`,
0.867) против «дорого в сумме» (`Legal Review Started`, 69.9 млрд ₽).

## DATA-T4-06: Покрытие топ-10 считается по частотам, а не суммой округлённых долей

**Дата:** 2026-10-31
**Проблема:** `top10_coverage_percent` суммировал уже округлённые `share_percent` (по 2 знака),
из-за чего 44 198 / 50 000 = **88.40%** превращались в 88.41%. Бейдж на сайте и итоговая строка
таблицы расходились бы на 0.01 п.п.
**Решение:** покрытие = `round(top10_cases / total_cases * 100, 2)`; в JSON добавлено поле
`top10_cases` = 44 198. Доли отдельных вариантов остаются округлёнными — итог таблицы берётся
из `top10_coverage_percent`, а не складывается на клиенте.
**Следствие:** `variants.json` → `top10_coverage_percent = 88.4`, info-badge показывает 88.4%.

## DATA-T4-07: В `process_map.json` добавлены `edges_by_category`

**Дата:** 2026-10-31
**Контекст:** фильтр по категории на вкладке Process Map изначально менял только размер узлов
(`frequency_by_category`). Рёбра оставались общими по всему логу, то есть граф «ЗИП» показывал
переходы, посчитанные по всем 50 000 кейсам.
**Решение:** добавлено `edges_by_category` — `{category: [{activity, next_activity, frequency,
avg_duration_days}]}` по 5 категориям. Сайт при выборе категории пересчитывает и узлы, и рёбра.
**Проверка:** в каждой категории по 28 переходов; сумма частот по 5 категориям совпадает
с общим списком `edges` до перехода (расхождений 0) — каждый кейс принадлежит ровно одной категории.
**Следствие:** `process_map.json` 14.8 → 28.3 КБ. Набор узлов от категории не зависит (все 25
активностей есть в каждой категории), меняются частоты и толщина рёбер.
