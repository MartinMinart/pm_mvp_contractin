## 1. Общие сведения

Документ описывает модель данных event log для Process Mining по процессу закупок и контрактации. Модель фиксирует границы процесса, сквозной идентификатор, объекты контроля, перечень событий и правила преобразования данных. Источник истины для полей и статистики — `docs/data_overview.md`; правила склейки кейсов — `spec/data_model.md`.

**Назначение модели:**

- собрать корректный event log из двух плоских таблиц (`cases.csv`, `events.csv`);
- обеспечить воспроизводимый расчёт KPI, узких мест и вариантов процесса;
- служить контрактом между генератором данных, валидатором и статическим сайтом.

**Границы ответственности документа:**

- входит: структура таблиц, типы полей, связи, S2T-маппинг, способ агрегации;
- не входит: регламент закупочной деятельности, юридические требования к договорам, production-интеграция с SAP.

## 2. Описание модели данных процесса

### 2.1. Границы процесса

| Параметр | Значение |
|---|---|
| Начало процесса | `Requisition Created` — заявка на закупку создана |
| Окончание процесса | `Payment Made` — оплата произведена |
| Анализируемый контур | Закупка → Контрактация → Логистика → Исполнение |
| Период данных MVP | 2024-01 — 2024-12 (12 месяцев) |
| Объём MVP | 50 000 кейсов, 1 094 474 события, 25 активностей |
| Тип данных | Синтетические, обезличенные, `SEED = 42` |

### 2.2. Сквозной идентификатор

**`case_id`** — номер закупки. Один `case_id` объединяет все события от создания заявки до оплаты. Формат: `CASE-000001` (префикс `CASE-` + 6 цифр).

Правила:

- `case_id` уникален в `cases.csv`;
- каждый `case_id` из `events.csv` обязан существовать в `cases.csv` (referential integrity);
- события одного кейса упорядочены по `timestamp`;
- дубликаты `(case_id, activity, timestamp)` не допускаются.

### 2.3. Объекты контроля

| Объект контроля | Логическая граница | Представление в модели MVP |
|---|---|---|
| **Закупка (Requisition)** | От `Requisition Created` до выбора поставщика и создания проекта договора | Набор событий кейса с `phase = sourcing`; ключ — `case_id` |
| **Договор (Contract)** | От `Draft Contract Created` до `Signed by Supplier` | Набор событий кейса с `phase = contracting`; ключ — `case_id` |
| **Платёж (Payment)** | От `Invoice Received` до `Payment Made` | Набор событий кейса с `phase = execution`; ключ — `case_id` |

В MVP объекты контроля не вынесены в отдельные таблицы: они представлены фазами (`phase`) и группами активностей внутри одного кейса. Отдельные `contract_id` и `payment_id` появятся на втором этапе при интеграции с SAP.

## 3. Модель данных

### 3.1. Схема связей

```text
┌────────────────────┐         ┌────────────────────┐
│     cases.csv      │ 1     N │     events.csv     │
│  (атрибуты кейса)  │─────────│     (события)      │
└────────────────────┘ case_id └────────────────────┘
```

- `cases.csv` — одна строка = один кейс (закупка).
- `events.csv` — одна строка = одно событие кейса.
- Связь: `cases.csv (1) — events.csv (N)` по полю `case_id`.
- Тип связи: «один ко многим», обязательная сторона — `events.csv`.

### 3.2. Перечень используемых таблиц

| № | Таблица | Роль | Строк в MVP | Ключ | Источник |
|---|---|---|---|---|---|
| 1 | `data/processed/cases.csv` | Справочник кейсов | 50 000 | `case_id` | `tools/generate_synthetic.py` |
| 2 | `data/processed/events.csv` | Event log | 1 094 474 | `(case_id, activity, timestamp)` | `tools/generate_synthetic.py` |

Обе таблицы генерируются локально и не коммитятся в Git. Для сайта используются производные агрегаты в `site/data/*.json`.

## 4. Описание таблиц

### 4.1. `cases.csv` — атрибуты кейса

| Поле | Тип | Обязательность | Описание |
|---|---|---|---|
| `case_id` | string | Да | Уникальный идентификатор кейса, формат `CASE-000001` |
| `category` | string | Да | Категория закупки: ЗИП (запчасти), Подрядные работы, Спецтехника, Обслуживание оборудования, Химические реагенты |
| `procurement_type` | string | Да | Тип закупки: Тендер, Запрос котировок, Рамочный договор, Единственный поставщик |
| `region` | string | Да | Регион: Кировск, Апатиты, Ковдор, Мурманск |
| `department` | string | Да | Подразделение / роль-владелец кейса |
| `supplier` | string | Да | Обезличенный поставщик, формат `Поставщик_XXX` |
| `currency` | string | Да | Валюта, в MVP — `RUB` |
| `amount` | float | Да | Сумма контракта, руб. |
| `downtime_cost_per_day` | int | Да | Стоимость простоя, руб./день |
| `is_import` | int | Да | Признак импортной закупки: `0` / `1` |
| `is_rejected` | int | Да | Признак отмены кейса: `0` / `1` |

### 4.2. `events.csv` — события процесса

| Поле | Тип | Обязательность | Описание |
|---|---|---|---|
| `case_id` | string | Да | Внешний ключ к `cases.csv` |
| `activity` | string | Да | Название активности из справочника (25 шагов) |
| `timestamp` | ISO 8601 | Да | Дата и время события |
| `resource` | string | Да | Роль исполнителя (без ФИО) |
| `phase` | string | Да | Фаза: `sourcing`, `contracting`, `logistics`, `execution` |
| `source_system` | string | Да | Система-источник: `SAP SRM`, `SAP ERP`, `ЭДО` |
| `document_type` | string | Нет | Тип документа; в MVP пусто на 100% |
| `document_status` | string | Нет | Статус документа; в MVP пусто на 100% |
| `category` | string | Да | Категория закупки (денормализовано из `cases.csv`) |
| `procurement_type` | string | Да | Тип закупки (денормализовано) |
| `region` | string | Да | Регион (денормализовано) |
| `department` | string | Да | Подразделение / роль-владелец (денормализовано) |
| `supplier` | string | Да | Поставщик (денормализовано) |
| `amount` | float | Да | Сумма контракта, руб. (денормализовано) |
| `is_import` | int | Да | Признак импорта: `0` / `1` |
| `is_rejected` | int | Да | Признак отмены: `0` / `1` |
| `downtime_cost_per_day` | int | Да | Стоимость простоя, руб./день |

**Правила качества:**

- `case_id` и `timestamp` не могут быть пустыми;
- `timestamp` парсится как ISO 8601;
- события одного кейса не могут идти раньше предыдущего события;
- дубликаты `(case_id, activity, timestamp)` запрещены;
- все `case_id` из `events.csv` присутствуют в `cases.csv`.

## 5. S2T-маппинг (Source-to-Target)

Таблица соответствия полей источника (SAP SRM / ERP) и целевой модели `events.csv`. В MVP не используется, так как синтетика уже в целевом формате; документ нужен для второго этапа интеграции.

| Источник (SAP SRM / ERP) | Целевое поле (`events.csv`) | Трансформация |
|---|---|---|
| `REQ_ID` | `case_id` | `'CASE-' + lpad(REQ_ID, 6, '0')` |
| `ACTIVITY_CODE` | `activity` | Маппинг через `spec/activity_dictionary.md` |
| `EVENT_TIMESTAMP` | `timestamp` | `to_iso8601(ts)` |
| `USER_ROLE` | `resource` | Маппинг через справочник ролей |
| `PROCESS_PHASE` | `phase` | Константа по активности |
| `SYSTEM_NAME` | `source_system` | Константа по источнику |
| `CATEGORY_ID` | `category` | JOIN со справочником категорий |
| `PROC_TYPE` | `procurement_type` | Константа |
| `REGION_ID` | `region` | JOIN со справочником регионов |
| `DEPT_ID` | `department` | JOIN со справочником подразделений |
| `SUPPLIER_ID` | `supplier` | `'Поставщик_' + lpad(SUPPLIER_ID, 3, '0')` |
| `AMOUNT_RUB` | `amount` | `cast(amount as float)` |
| `DOWNTIME_COST` | `downtime_cost_per_day` | Константа по категории |

## 6. Скрипты и триггеры

В MVP нет СУБД и серверных триггеров. Роль «триггера» выполняет ETL-скрипт, который запускается вручную после генерации или обновления CSV.

| Компонент | Роль | Вход | Выход |
|---|---|---|---|
| `tools/csv_to_json.py` | Агрегатор / условный «триггер» | `data/processed/events.csv`, `data/processed/cases.csv` | 5 JSON в `site/data/` |
| `tools/validate.py` | Предварительный контроль качества | `events.csv`, `cases.csv` | Отчёт валидации, код возврата |
| `tools/generate_synthetic.py` | Генератор исходных данных | `SEED = 42` | `events.csv`, `cases.csv` |

**Логика `csv_to_json.py`:**

1. читает сырые CSV;
2. считает KPI, срезы, DFG, узкие места и варианты;
3. записывает `overview.json`, `process_map.json`, `bottlenecks.json`, `variants.json`, `variant_paths.json`;
4. не изменяет исходные CSV.

**Порядок запуска:**

```bash
python tools/generate_synthetic.py   # генерация CSV
python tools/validate.py             # проверка качества
python tools/csv_to_json.py          # агрегация в JSON
python -m http.server 8000           # локальный просмотр сайта
```

## 7. Ограничения и допущения

- Данные **синтетические**, не содержат реальных закупок и ПДн.
- В `events.csv` поля `document_type` и `document_status` пусты на 100% — задел на второй этап.
- Отдельных сущностей `contract_id` и `payment_id` нет: договор и платёж представлены группами активностей внутри кейса.
- `variant_paths.json` содержит только топ-15 маршрутов, хотя `variants.json` знает про 80 вариантов.
- Case-level drill-down в интерфейсе не реализован: панель показывает агрегаты переходов и узлов.
- S2T-маппинг описан документально, но не автоматизирован.
